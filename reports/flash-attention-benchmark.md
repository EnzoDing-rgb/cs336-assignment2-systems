# FlashAttention 性能测试报告

<!-- report:hand-maintained -->

## 1. 我们在比什么

机器是一块 **NVIDIA A800（80GB 显存）**。每次只跑 **1 条序列**（batch=1），并且打开 **因果掩码**（每个位置只能看自己和前面的位置）。

每个配置都测三项，单位都是毫秒（取多次运行的中位数）：

1. **只跑前向**
2. **只跑反向**（在已经算好的前向结果上反传）
3. **前向+反向连在一起**（更接近训练时一步的开销）

### 1.1 三种实现（对照关系）

这次一共对比 **三种实现**，名字如下。不要把它们都叫成 baseline：真正的「朴素对照」只有第一种。

| 名称 | 前向怎么做 | 反向怎么做 |
|------|------------|------------|
| **朴素注意力**（naive attention） | 先算出整张 $S\times S$ 的分数矩阵，再做 Softmax | 走 PyTorch 普通自动求导 |
| **Flash（PyTorch 版）** | 按作业 Algorithm 1，用 Python 循环分块算，避免长期保存整张大矩阵 | 用公式把注意力权重重新算出来（仍是整张大矩阵量级），再用 `torch.compile` 加速这段代码 |
| **Flash（Triton 版）** | 用 Triton 把分块计算融进少量 GPU 内核，中间结果尽量留在片上 | 同样用 Triton 做分块反向（Algorithm 2） |

主对比里，两个 Flash 版本使用 **同一套分块大小**（由 `_choose_flash_tiles(序列长度, 隐藏维)` 决定）。这样比出来的快慢，主要反映「代码怎么在 GPU 上执行」，而不是「谁切的块更大」。

### 1.2 实际做了哪两轮实验（以跑出来的为准）

**实验 A：三种实现的主对比**

- 序列长度 $S$：128 到 65536  
- 隐藏维 $d$：16、32、64、128  
- 数据类型：fp32、bf16  
- **三种实现都参与**：朴素注意力、Flash（PyTorch 版）、Flash（Triton 版）

但有几条必须说清楚的限制（都是实测结果，不是口号）：

1. **Flash（PyTorch 版）在主对比里只测到 $S\le 2048$。**  
   原因：它用 Python 双层循环按小块调用很多小算子。序列一长，单次前向就要数秒甚至更久；再乘计时函数的多次重复，整张大表跑不完。所以主表里更长序列对它标成 `skip`。更长序列上「加大分块能不能救 PyTorch 版」放到实验 B 看。

2. **Flash（PyTorch 版）的 bf16 全部失败。**  
   报错是数据类型不一致（输入是 bf16，中间累加写成了 float）。主表里 bf16 对应行是 `err`。**因此 bf16 下只能认真看「朴素注意力」和「Flash（Triton 版）」**；不要把 PyTorch 版的 `err` 当成「很慢」。

3. **朴素注意力在 fp32、$S=65536$ 时：前向往往还能跑完，反向显存不够（OOM）。**  
   表里会看到「前向有数字，反向/端到端是 OOM」。我们约定：某个实现一旦在某个 $(d, 数据类型)$ 上 OOM，**更大的 $S$ 不再继续测**（直接 skip）。这次朴素注意力的 OOM 主要出现在最长档，后面已经没有更大的 $S$ 需要再 skip。

4. **Flash（Triton 版）在主对比的网格里基本都跑通了**（含很长的 $S$）。

**实验 B：只比两个 Flash，专门看「分块大小」**

这一轮 **没有朴素注意力**，只比：

- Flash（PyTorch 版）
- Flash（Triton 版）

固定用 fp32，选了几组 $(S,d)$，再手动改分块边长（16、32、64、128，以及「自动选择」那一档）。想回答两件事：

- PyTorch 版把块切大一点，能快多少？  
- Triton 版块切太大时，会不会因为片上共享内存不够而直接失败？

## 2. 实验 A：主对比图在说什么

### 2.1 前向时间随序列长度怎么变

<img src="figures/flash_bench_forward_vs_seq.png" alt="flash_bench_forward_vs_seq.png" width="780" />

先看 fp32、隐藏维 $d=64$、序列长度 $S=32768$ 这个点（主对比里 PyTorch 版已经 skip，所以只剩两条）：

- 朴素注意力前向约 **54.5 ms**  
- Flash（Triton 版）前向约 **7.7 ms**，大约快 **7 倍**

原因很直白：朴素做法要把 $S\times S$ 那么大的中间结果在显存里读写；Triton 版按块在片上做完 Softmax 相关计算，少搬很多数据。序列越长，这个差距通常越明显。

再看短序列（比如几百）：几条线会挤在一起，甚至朴素有时也不慢。因为这时大矩阵还不大，而启动内核、编译等固定开销占比重更大，看不出长序列那种「搬数据」的优势。

Flash（PyTorch 版）在 $S\le 2048$ 的格子里，前向往往 **比朴素慢很多**（常见是几百到几千毫秒）。它虽然也是「分块 Flash 算法」，但执行方式是 Python 循环 + 大量小算子，没有把一整段计算融进少数高效内核。所以：**算法名字带 Flash，不等于跑起来像 Triton。**

### 2.2 反向时间随序列长度怎么变

<img src="figures/flash_bench_backward_vs_seq.png" alt="flash_bench_backward_vs_seq.png" width="780" />

还是 $d=64$、fp32、$S=32768$：

- 朴素注意力反向约 **59.5 ms**  
- Flash（Triton 版）反向约 **24.0 ms**，大约快 **2.5 倍**

这一点很重要：Triton 版反向也是分块实现，所以 **不会** 再跟朴素「几乎打平」。  
Flash（PyTorch 版）的反向仍然要重新构造整张注意力权重量级的中间量，在它测得到的短序列上，反向时间通常和朴素同一个量级，前向反而才是它特别慢的地方。

### 2.3 前向+反向总时间随序列长度怎么变

<img src="figures/flash_bench_e2e_vs_seq.png" alt="flash_bench_e2e_vs_seq.png" width="780" />

同样锚点：

- 朴素：约 **114 ms**  
- Flash（Triton 版）：约 **31.7 ms**，大约快 **3.6 倍**

总时间大致是「前向 + 反向」。Triton 版前向已经很快，总时间更多被反向拖住，所以总加速比（约 3.6 倍）小于前向加速比（约 7 倍）。这是正常现象，不是测错了。

### 2.4 时间随隐藏维 $d$ 怎么变

下面三张图固定几个序列长度，横轴换成隐藏维。

<img src="figures/flash_bench_forward_vs_d.png" alt="flash_bench_forward_vs_d.png" width="780" />

矩阵乘的量会随 $d$ 变大；朴素实现还要额外处理那张与 $d$ 关系不大的 $S\times S$ 大表。所以当 $d$ 变大时，大家都会变慢，而「只靠少搬大表」带来的相对优势，常常会看起来不那么夸张。Triton 在 $d$ 很大时还会主动选用更小的分块（怕片上内存不够），启动次数变多，曲线也会更陡一些。

<img src="figures/flash_bench_backward_vs_d.png" alt="flash_bench_backward_vs_d.png" width="780" />

反向图里，Triton 版在多数能比的点上仍低于朴素；PyTorch 版只出现在较短 $S$ 的曲线上，且反向并不突出地快。

<img src="figures/flash_bench_e2e_vs_d.png" alt="flash_bench_e2e_vs_d.png" width="780" />

总时间图就是前向图和反向图叠在一起的结果。读的时候最好对照同一配置的前向、反向，不要单独盯着总时间讲故事。

## 3. 实验 B：分块大小到底有多重要

这一节 **只对比 Flash（PyTorch 版）和 Flash（Triton 版）**，没有朴素注意力。

<img src="figures/flash_bench_tile_ablation.png" alt="flash_bench_tile_ablation.png" width="780" />

横轴是分块边长（查询块和键块一样大）。虚线是 PyTorch 版，点线是 Triton 版；颜色区分不同的 $(S,d)$。

实测规律：

1. **PyTorch 版对分块大小极其敏感。**  
   例如 $S=2048$、$d=64$：分块 16 时前向约 **4339 ms**；分块 128 时约 **71 ms**，快了大约 **60 倍**。块越大，Python 循环次数越少，每次矩阵乘也更大，更划算。

2. **即使把块加大，PyTorch 版通常仍远远慢于同设置下的 Triton 版。**  
   同上配置，Triton 在能跑的分块上前向大约是 **0.1～0.2 ms** 量级。说明：加大分块能补救「循环太碎」，但补不了「没有融合成高效内核」。

3. **Triton 版不是块越大越好，太大了会直接失败。**  
   失败原因是片上共享内存不够（日志里是 `OutOfResources: shared memory`），不是普通的整卡显存 OOM。例如 $d=64$ 时 128×128 多次失败；$d=128$ 时连 64×64 也可能失败。所以「自动选择分块」的意义，是在 **能跑通** 的前提下选一个较合适的大小，而不是盲目取最大。

4. **自动选择那一档，对 PyTorch 版有时并不友好。**  
   例如 $S=8192$、$d=128$ 时自动选成 16×16，PyTorch 版前向约 **70600 ms**（七十秒量级）；同点 Triton 约 **2.2 ms**。自动策略主要是按 Triton 的片上内存限制写的，拿去约束 PyTorch 版，会显得特别惨——这恰好说明「同一套分块」和「对谁最优」不是一回事。

## 4. 总结论

1. **长序列前向：Flash（Triton 版）明显快于朴素注意力**；快的核心是少把 $S\times S$ 大表在显存里来回搬，而不是名字里有 Flash 三个字。

2. **Flash（PyTorch 版）是「算法对了、执行形态还很重」的对照。**  
   在它测得到的范围内，前向常常远慢于朴素；反向则和朴素同一量级。它证明了分块公式可以在纯 PyTorch 里写出来，但 **不能** 代表融合内核的速度。

3. **反向也做成 Triton 分块之后，反向和总时间都会比朴素好**；但总加速比通常小于前向加速比，因为反向仍然更贵。

4. **分块大小是另一件独立的事。**  
   加大分块能大幅挽救 PyTorch 版的前向，却仍追不上 Triton；Triton 分块太大则可能直接因共享内存失败。主对比用相同分块，是为了先把「执行方式」比清楚；实验 B 再单独把「分块大小」拆开看。
