# FlashAttention 性能测试报告

<!-- report:hand-maintained -->

## 1. 我们在比什么

机器是一块 **NVIDIA A800（80GB 显存）**。每次只跑 **1 条序列**（batch=1），并且打开 **因果掩码**（每个位置只能看自己和前面的位置）。

每个配置都测三项，单位都是毫秒（取多次运行的中位数）：

1. **只跑前向**
2. **只跑反向**（在已经算好的前向结果上反传）
3. **前向+反向连在一起**（更接近训练时一步的开销）

图里：实心柱 = 实测；斜线淡色柱 = **外推估计**（不是实测，规则见 §1.3）；缺柱 = 该实现在该点 OOM 或未跑通。

### 1.1 三种实现（对照关系）

这次一共对比 **三种实现**。真正的「朴素对照」只有第一种；后两种都是 FlashAttention-2 路线，但执行形态差很远。

| 名称 | 前向怎么做 | 反向怎么做 |
|------|------------|------------|
| **朴素注意力**（naive attention） | 先在显存里写出整张 $S\times S$ 的分数矩阵，再 Softmax、再乘 $V$ | 走 PyTorch 普通自动求导，中间大矩阵的梯度也要在显存里走一遍 |
| **Flash（PyTorch 版）** | 按作业 Algorithm 1：Python 双层循环按块算，块内用普通矩阵乘，长期不保存整张大分数矩阵 | 按公式把注意力权重矩阵量级的中间量 **重新算出来**（仍是整张 $S\times S$ 量级），再用 `torch.compile` 把这段稠密重算编译加速 |
| **Flash（Triton 版）** | Triton 把「分块读 $Q/K/V$ → 片上 Softmax 归约 → 写回 $O$」融进少量 GPU 内核 | Triton 分块反向（Algorithm 2）：同样尽量在片上完成，避免把整张注意力权重长期放在显存 |

### 1.2 两轮实验分别回答什么

**实验 A：三种实现的主对比**

- 序列长度 $S$：128 … 65536  
- 隐藏维 $d$：16、32、64、128  
- 数据类型：fp32、bf16  
- 短序列（$S\le 2048$）上，两个 Flash 尽量用同一套自动分块（`_choose_flash_tiles`），好把差异归因到「怎么在 GPU 上执行」。  
- 更长序列上，Flash（PyTorch 版）若仍用自动小分块，Python 循环会拖到分钟级，整张表跑不完。因此长序列补测时 **刻意加大分块**（记作 `longS(64×64)` / `longS(128×128)`），并在表里写明。这和 Triton 主对比里的自动分块 **不完全相同**，读数时要分开看。

**实验 B：只比两个 Flash，专门动分块大小**

没有朴素注意力。固定几组 $(S,d)$（fp32），手动扫 16/32/64/128 以及自动档，看：加大分块能救多少 PyTorch；Triton 分块太大会不会因片上共享内存失败。

### 1.3 长序列 Flash（PyTorch 版）：哪些是测的，哪些是估的

**实测（实心柱）**

- fp32、$d=16$：一直测到 $S=65536$（加大分块）  
- fp32、$d=32$：测到 $S=32768$  
- fp32、$d=64$：补测了 $S=4096,8192,16384$（加大分块；约 2 分钟跑完这三格）  
- 短序列 $S\le 2048$：fp32 / bf16 都有实测（bf16 路径已修好，不再是类型报错）

**估计（斜线柱，数字后带 `*`）**

外推只填 Flash（PyTorch 版）主表缺口，规则尽量保守、可复查：

1. **同一 $d$、同一加大分块族内**：前向按 $(S/\text{tile})^2$ 放大（Python 双层循环次数大致如此）；反向按 $S^2$ 放大（稠密重算注意力权重量级）。锚点优先用同 $d$ 上最近的实测长序列点。  
2. **缺的 $d=128$ 长序列**：前向几乎不随 $d$ 变（循环开销压过矩阵乘），取同 $S$ 上 $d=64$ 前向略放大；反向用同 $S$ 上 $d=32$ 与 $d=64$ 的斜率外推到 128。  
3. **bf16 长序列**：用同 $(S,d)$ 的 fp32（实测或已估）乘「短序列上 bf16/fp32 的中位比值」。

朴素注意力在 fp32、$S=65536$ 反向 OOM：图上留空，不做假估计。

## 2. 实验 A：主对比图在说什么

主图固定看 $d=64$（左右 fp32 / bf16）。每个 $S$ 上最多三根柱：蓝=朴素，橙=Flash-PyTorch，绿=Flash-Triton。

### 2.1 前向时间随序列长度

<img src="figures/flash_bench_forward_vs_seq.png" alt="flash_bench_forward_vs_seq.png" width="820" />

先盯 fp32、$d=64$、$S=32768$：

- 朴素前向约 **54.5 ms**  
- Flash（Triton）约 **7.7 ms**，大约快 **7 倍**  
- Flash（PyTorch）此处是斜线估计，大约 **18.5 秒** 量级——比朴素慢两个数量级以上

**为什么 Triton 能快。** 朴素要把大约 $S\times S$ 的中间结果在高带宽显存（HBM）里写出来再读回去。$S=32768$ 时，单张 fp32 分数矩阵就大约 $32768^2\times 4$ 字节 ≈ 4GB 量级，前后还要配 Softmax、乘 $V$ 等多次往返。Triton 按块把 $Q/K/V$ 搬进片上存储，在片上做完局部 Softmax 归约再写回输出；显存流量从「整表级」降到「按块进出」。序列越长，省下的搬运越值钱，所以长 $S$ 上绿柱相对蓝柱越来越矮。

**为什么短序列差距会缩小。** $S$ 只有几百时，大表还不巨大，而启动内核、编译、同步等固定开销占比重更大；有时朴素也不慢。这时「少搬大表」的优势还没完全展开。

**为什么 Flash（PyTorch）前向可以比朴素慢很多。** 它算的也是分块 Flash 公式，但执行是：Python 解释器两层循环 × 每一小块若干次小矩阵乘/逐元素算子。每次小算子都要经历一次「从 Python 下到 GPU」的调度。循环次数大致随 $(S/\text{tile})^2$ 涨。把 tile 从 16 提到 128，循环少了约 64 倍，前向会从数秒掉到几十毫秒（见实验 B）——但即使如此，仍远慢于把整段逻辑融进少数 Triton 内核。所以：**算法名字带 Flash，不等于跑起来像融合内核。**

一个很刺眼的实测现象：加大分块后，$S=4096$（tile 64）前向约 **1159 ms**，$S=8192$（tile 128）约 **1168 ms**——几乎一样。因为块边长翻倍，循环次数大约降到四分之一，正好抵消了序列加倍带来的工作量；再翻到 $S=16384$、仍用 tile 128，循环次数约再 ×4，前向就到约 **4625 ms**。这和「按 $(S/\text{tile})^2$ 粗外推」是对得上的。

bf16 侧：朴素和 Triton 都比同点 fp32 更快一些（更窄的数据类型、更省带宽）；Flash（PyTorch）短序列实测仍是秒级，长序列斜线柱来自 fp32×短序列比值，形状与 fp32 类似。

### 2.2 反向时间随序列长度

<img src="figures/flash_bench_backward_vs_seq.png" alt="flash_bench_backward_vs_seq.png" width="820" />

同一锚点 fp32、$d=64$、$S=32768$：

- 朴素反向约 **59.5 ms**  
- Flash（Triton）约 **24.0 ms**，大约快 **2.5 倍**  
- Flash（PyTorch）估计反向约 **59 ms**，和朴素同一量级

**反向为什么普遍比「Triton 前向」贵。** 反向至少要再碰一遍与注意力权重同量级的信息：要么像朴素那样对已保存的大中间量反传，要么像 Flash 那样为了省前向显存而 **重新构造** 这些量再反传。重新构造本身就要读 $Q/K/V/O$、再做大量乘加，显存与计算都重。

**Triton 反向为什么仍能赢朴素。** 它的反向也是分块、片上完成关键归约，不会先在显存里摊开一张完整的注意力权重再求导。所以绿柱在长 $S$ 上稳定低于蓝柱，而不是「前向很快、反向却和朴素打平」。

**Flash（PyTorch）反向为什么相对「不那么惨」。** 它的反向路径是：稠密地重算注意力权重量级中间量 + `torch.compile` 编译后的大核。编译后的大矩阵乘，吞吐远好于前向那种「Python 碎循环」。于是出现一个反差：**前向要秒～几十秒，反向往往只要毫秒～几十毫秒。** 例如实测 $S=16384$、$d=64$、fp32：前向 **4625 ms**，反向只有 **14.9 ms**。端到端几乎被前向单独拖死。

fp32、$S=65536$ 时朴素反向 OOM（缺蓝柱），Triton 仍约 **91 ms**；Flash（PyTorch）反向是斜线估计。

### 2.3 前向+反向总时间

<img src="figures/flash_bench_e2e_vs_seq.png" alt="flash_bench_e2e_vs_seq.png" width="820" />

锚点 $S=32768$、$d=64$、fp32：

- 朴素约 **114 ms**  
- Triton 约 **31.7 ms**，大约快 **3.6 倍**  
- Flash（PyTorch）估计约 **18.6 秒**

总加速比（约 3.6×）小于前向加速比（约 7×），原因很直接：总时间 ≈ 前向 + 反向。Triton 前向已经压得很低，反向仍占大头（约 24 ms vs 前向 7.7 ms），所以「前向省下来的」摊到总和里会被反向稀释。这是结构如此，不是测错。

Flash（PyTorch）的总时间几乎等于前向：反向再快，也救不了 Python 分块循环。

### 2.4 时间随隐藏维 $d$

下面三张图固定 $S\in\{512,2048,8192\}$，横轴换 $d$（fp32）。$S=8192$ 上橙色若带斜线，表示该 $d$ 来自估计（本轮 $d=128$ 长序列多为估计；$d=16/32/64$ 在 $S=8192$ 为实测加大分块）。

<img src="figures/flash_bench_forward_vs_d.png" alt="flash_bench_forward_vs_d.png" width="820" />

矩阵乘的计算量随 $d$ 涨。朴素还要额外伺候那张与 $d$ 关系不大的 $S\times S$ 大表，所以当 $d$ 变大时，大家都会变慢，但「只靠少搬大表」带来的相对优势有时看起来不那么夸张。Triton 在 $d$ 很大时会主动选更小分块（怕片上内存不够），启动次数变多，曲线会更陡——例如 $d=128$ 时常落到 16×16 自动分块。

Flash（PyTorch）前向在加大分块后，对 $d$ 几乎不敏感：柱高差不多。因为时间预算被 Python 循环次数吃掉了，多乘一点 $d$ 相对不显眼。

<img src="figures/flash_bench_backward_vs_d.png" alt="flash_bench_backward_vs_d.png" width="820" />

反向更吃「与 $d$ 相关的矩阵乘」以及重算时的带宽。Triton 多数点仍低于朴素；PyTorch 反向随 $d$ 缓慢上升，但仍远小于它自己的前向。

<img src="figures/flash_bench_e2e_vs_d.png" alt="flash_bench_e2e_vs_d.png" width="820" />

总时间图 = 前向图与反向图叠在一起。读时最好同一 $(S,d)$ 对照三项，不要单独盯总时间讲故事。

## 3. 实验 B：分块大小到底有多重要

这一节 **只对比两个 Flash**，没有朴素注意力。下图是 $S=2048$、$d=64$、fp32 的分组柱。

<img src="figures/flash_bench_tile_ablation.png" alt="flash_bench_tile_ablation.png" width="820" />

| 序列长度 | 隐藏维 | 分块 | PyTorch 前向/反向/总时间 | Triton 前向/反向/总时间 |
|---:|---:|:-----|:--------------------------|:-------------------------|
| 2048 | 64 | 16×16 | 4339 / 0.98 / 4302 | 0.18 / 0.58 / 0.74 |
| 2048 | 64 | 32×32 | 1101 / 0.34 / 1108 | 0.10 / 0.30 / 0.38 |
| 2048 | 64 | 64×64 | 281 / 1.05 / 284 | 0.12 / 0.41 / 0.50 |
| 2048 | 64 | 128×128 | 70.6 / 0.98 / 71.5 | 失败（共享内存不够） |
| 2048 | 64 | 自动(32×32) | 1099 / 0.34 / 1106 | 0.10 / 0.30 / 0.53 |
| 4096 | 64 | 32×32 | 4364 / 1.08 / 4418 | 0.28 / 0.81 / 1.07 |
| 4096 | 64 | 64×64 | 1121 / 1.08 / 1109 | 0.23 / 0.59 / 0.79 |
| 4096 | 64 | 128×128 | 286 / 1.08 / 280 | 失败（共享内存不够） |
| 8192 | 64 | 64×64 | 4488 / 4.13 / 4337 | 0.88 / 2.22 / 3.04 |
| 8192 | 64 | 128×128 | 1099 / 4.13 / 1091 | 失败（共享内存不够） |
| 8192 | 64 | 自动(32×32) | 17450 / 4.13 / 17794 | 0.71 / 2.26 / 2.95 |
| 8192 | 128 | 自动(16×16) | 70600 / 6.25 / 70211 | 2.18 / 9.53 / 11.6 |

读表时注意四件事：

1. **PyTorch 对分块极其敏感。** $S=2048$、$d=64$：tile 16 → 约 4339 ms；tile 128 → 约 71 ms，大约快 60 倍。块越大，循环越少，每次矩阵乘越大，越划算。  
2. **加大分块仍追不上 Triton。** 同上配置 Triton 前向约 0.1～0.2 ms。救的是「循环太碎」，救不了「没有融合成高效内核」。  
3. **Triton 不是块越大越好。** 太大直接 `shared memory` 资源不足（不是整卡 OOM）。$d=64$ 时 128×128 多次失败。自动分块的意义是在「能跑通」的前提下选较合适的大小。  
4. **自动档对 PyTorch 有时很不友好。** 例如 $S=8192$、$d=128$ 自动成 16×16，PyTorch 前向约 70 秒；同点 Triton 约 2.2 ms。自动策略主要按 Triton 片上内存限制写，拿去绑 PyTorch，会显得特别惨——这也说明「同一套分块」和「对谁最优」不是一回事。主对比长序列给 PyTorch 单独加大分块，正是为了在「还能测完」的前提下补全橙色柱。

一个值得单独写的现象：**tile 从 32 提到 64，有时 Triton 前向几乎不更快，甚至略慢。** 块变大，单次内核工作量变大、共享内存占用变高，占用率/并行度可能下降；再大就直接失败。所以「更大」不是单调更优，存在能跑通的甜点区。

## 4. 总结论

1. **长序列前向：Flash（Triton）明显快于朴素注意力**；快的核心是少把 $S\times S$ 大表在显存里来回搬，并融合成少量内核。  
2. **Flash（PyTorch）是「算法对了、执行形态还很重」的对照。** 前向常被 Python 分块循环拖成秒级甚至更长；反向因稠密重算 + `torch.compile`，往往只要毫秒级，和朴素同一量级。它证明分块公式可以在纯 PyTorch 里写出来，但 **不能** 代表融合内核的速度。  
3. **反向也做成 Triton 分块后，反向和总时间都会好于朴素**；总加速比通常小于前向加速比，因为反向仍然更贵，会稀释前向省下的时间。  
4. **分块大小是另一件独立的事。** 加大分块能大幅挽救 PyTorch 前向，却仍追不上 Triton；Triton 分块太大可能因共享内存失败。主对比短序列尽量同自动分块；长序列 PyTorch 使用更大的 `longS` 分块，并在图/表中标明；缺口用斜线估计补齐，规则见 §1.3。
