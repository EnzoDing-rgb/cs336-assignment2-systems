ZeRO 技术说明

用 4 张卡、小数组把通信和分片跑一遍。无动画。看「开始每卡有什么 → 结束每卡有什么」。

场景 通信算子 朴素 DDP ZeRO-1 / Pos Stage 2/3 作业实现 核心差异：对齐 W 对照表 流量 / 带宽怎么算

0. 共用玩具场景

4 GPU rank 0–3  |  权重拍扁成 W = [w0…w7]（8 个数）

Adam 粗算：每卡若存全套，大约还有完整的 m[8]、v[8]。优化器状态很贵 → ZeRO 要切开存。

符号意思切什么
PosPartition Optimizer States切优化器状态 m, v
PgPartition Gradients切梯度
PpPartition Parameters切参数本身

Stage 1 = 只有 Pos  ·  Stage 2 = Pos+Pg  ·  Stage 3 = Pos+Pg+Pp

2. 朴素 DDP：每卡全套

每卡都有
  • W[8] 完整参数
  • G[8] 完整梯度
  • m[8], v[8] 完整 Adam 状态
一步
  1. 本地 forward / backward → 本地 G
  2. all-reduce 平均 G → 每卡 G 相同
  3. 用完整 (m,v) 更新完整 W

一步（一种常见调度）

A. 假设归约后梯度都是 G = [1,1,1,1,1,1,1,1]

B. 各卡只用自己的 m,v 更新自己分片：

卡1

卡2

↓ all-gather 参数分片
每卡结束
W = [w0', w1', w2', w3', w4', w5', w6', w7']

「只更新本分片权重 → 更新时只需要本分片梯度」——这句话对。
但请分清两件事：反传时整模仍会算出整条局部 G（每个参数位置都有数）； step 之后可以只保留与本分片对应的那截（或 reduce-scatter 后本来就只拿到那截）。 不是「反传只算 1/4 参数的 grad」。丢掉的是「用不上的那截存着」，不是跳过反传。

4. Stage 2 / 3（一眼）

Stage 2 = Pos+Pg

连梯度也按分片长期存放。卡0主要留 [g0,g1] + 对应 m,v。这比「step 时只用分片 grad」更进一步。

Stage 3 = +Pp

参数本身也只存分片；算之前 all-gather 拼出来，用完可丢掉。接近 FSDP。

5. 作业 ShardedOptimizer

为了和下一节对照公平，这里也用连续分片（与第 3 节同一套）：卡0管 w0–w1，卡1管 w2–w3，…（实现里是 i % world_size，归属规则不同，但「对齐新 W」的通信逻辑一样。）

step

  1. 本地 AdamW.step()：只改本分片
  2. 对齐新 W：对每个参数 broadcast(p.data, src=owner)（详见下一节 方案 A）

6. 核心差异：对齐新 W —— A = 多次 broadcast，B = 一次 all-gather

省 OPT、每卡只更新约 1/4 权重：作业和典型 ZeRO-1 同一类。
真正不一样、也值得数清楚「几次通信」的，是更新之后如何让每人都拿到完整新 W。

下面只盯这一步。假设本地 step 已经做完：各卡只把自己分片改成带撇的新值，别人的维仍是旧值。

共同起点（4 卡，W 共 8 个数）

卡本地刚更新的分片本卡完整 W 此刻长什么样（示意）
0w0', w1'[w0', w1', w2, w3, w4, w5, w6, w7]（后六维还是旧的）
1w2', w3'[w0, w1, w2', w3', w4, w5, w6, w7]
2w4', w5'[w0, w1, w2, w3, w4', w5', w6, w7]
3w6', w7'[w0, w1, w2, w3, w4, w5, w6', w7']

目标结束态（A、B 都一样）：每卡 W = [w0', w1', w2', w3', w4', w5', w6', w7']。

方案 A —— 作业：按 owner 多次 broadcast

API 语义：每次 broadcast(tensor, src=k) = 1 次集合通信调用： 全体参与，用卡 k 上的那份 tensor 覆盖所有人同名位置。

A1. 若 8 个独立参数（作业代码的真实写法：对每个 Parameter 调一次）

  1. broadcast(w0, src=0) → 四人的 w0 都变成 w0'
  2. broadcast(w1, src=0) → 四人的 w1 都变成 w1'
  3. broadcast(w2, src=1) → 四人的 w2 都变成 w2'
  4. broadcast(w3, src=1)
  5. broadcast(w4, src=2)
  6. broadcast(w5, src=2)
  7. broadcast(w6, src=3)
  8. broadcast(w7, src=3)

集体通信次数 = 8 次 broadcast（参数个数次）。

A2. 若先把每卡分片打成一块再发（教学对照用，作业没强制打包）

  1. broadcast([w0',w1'], src=0) → 四人下标 0,1 对齐
  2. broadcast([w2',w3'], src=1)
  3. broadcast([w4',w5'], src=2)
  4. broadcast([w6',w7'], src=3)

集体通信次数 = 4 次 broadcast（= world_size，每个 owner 发自己那一块）。

A 结束后卡0
[w0'…w7']
卡1
同上完整新 W
卡2
同上
卡3
同上

方案 B —— 典型 ZeRO-1：一次 all-gather 参数分片

API 语义：每人投入自己的一块 → 一次集体通信后，每人手里拼出全部块按顺序排好。

卡0 投入
shard0 = [w0', w1']
卡1 投入
shard1 = [w2', w3']
卡2 投入
shard2 = [w4', w5']
卡3 投入
shard3 = [w6', w7']
↓ 1 次 all-gather（拼 4 块）
每卡结束（同一次通信后）
W = concat(shard0…shard3) = [w0', w1', w2', w3', w4', w5', w6', w7']

集体通信次数 = 1 次 all-gather。

A 和 B 到底哪里不一样（数清楚）

A 作业（broadcast）B 典型 ZeRO-1（all-gather）
在干什么「这块以谁为准？→ 用 owner 覆盖所有人」「每人交出一块 → 每人拼齐全部块」
API 调用次数
（玩具 8 维 / 4 卡）		未打包：8 次 broadcast
按分片打包：4 次 broadcast		 1 次 all-gather
谁提供数据每次只有一个 src；别人那次只接收 每一次通信里，四卡都既发自己的分片、又收别人的分片
结束态每人完整新 W每人完整新 W（一样）
省不省 OPT一样省（都只养本分片 m,v）一样省

一句话

核心差异就是对齐新 W 这一步的集合通信形态： A = 多次 broadcast（按参数或按 owner 块）； B = 一次 all-gather（四块拼成完整 W）。 终点相同；次数与「谁在发」不同。

注：底层 NCCL 里一次 all-gather / 一次 broadcast 内部还可能拆成多段消息； 这里数的是你们在代码里发起的集体通信调用次数，这才是「日程」差异说得清的那一层。

8. 流量 / 带宽到底怎么算？

短答：不要用「集体通信调用了几次」当流量。 「8 次 / 4 次 broadcast」和「1 次 all-gather」说的是发起了几次算子（偏延迟 α）； 带宽要比的是搬了多少字节（偏体积 β）。 对「对齐新 W」这一步，A 和 B 要搬的有用数据量往往一样多；差在拆成几次发、消息多碎。

8.1 先扔掉一个误解

错误想法问题
4 次 broadcast = 4 份流量；1 次 all-gather = 1 份流量 把「调用次数」当成了「数据量」。一次很大的 all-gather 可以比四次很小的 broadcast 搬更多或一样多的字节。
all-gather 次数少，所以总带宽一定更省 次数少主要省的是启动开销 / 延迟；字节量要另算。对齐完整新 W 时，两边有用字节常常同阶甚至相同。

8.2 这一步信息论下界：每人缺多少？

仍用玩具：N=4 卡，完整 W 共 8 个数；每卡刚更新自己的 2 个数，缺另外 6 个新值。

卡0 已有
w0', w1'

还需 6 个数

卡1 已有
w2', w3'

还需 6

卡2 已有
w4', w5'

还需 6

卡3 已有
w6', w7'

还需 6

有用数据下界（只数「必须送到某卡的新分量」）：
每卡接收 ≥ 6 个元素 → 四卡合计 ≥ 24 个元素的「送达量」。
（设每个元素大小为 S 字节，则 ≥ 24S 字节的有用载荷被接收。）

A（多次 broadcast）和 B（一次 all-gather）都是为了填这 24 个空位；所以有用流量同阶，不是「1 对 4」。

8.3 按「有用送达量」逐项加总（教学账本）

约定：一次把大小为 M 的张量 broadcast 给 N 卡时，非 src 的 N−1 张卡各收到 M → 计入有用送达 (N−1)·M。all-gather 时，每卡收到别人的分片之和。

方案怎么发有用送达量（元素个数）集体调用次数
A1 8× broadcast（每次 1 个数） 每次：3 张非 src 卡各收 1 → 每次送达 3；×8 3×8 = 24 8
A2 4× broadcast（每次 1 个分片=2 个数） 每次：3 张卡各收 2 → 每次送达 6；×4 6×4 = 24 4
B 1× all-gather（4 块×2） 每卡收到另外 3 块×2 = 6；×4 卡 6×4 = 24 1

结论（对「对齐新 W」）

  • 有用字节：A1 = A2 = B = 24S（同一下界，打满）。
  • 不是「all-gather 只算一份流量、broadcast 算四份」。
  • 差别主要在：拆成几次集体通信（8 / 4 / 1），以及每次消息多碎。

8.4 时间怎么估：α–β 模型（把「次数」和「字节」拆开）

集合通信耗时常粗写成：

T ≈ α · (#集体调用或关键消息段)
  + β · (每卡沿关键路径搬动的字节数)
  • α：启动一次通信的固定开销（延迟）。调用越多，α 项越大 → 所以 8× 小 broadcast 往往比 1× all-gather 更亏在延迟。
  • β：每字节传输成本。有用字节相同时，β 项同阶；实现上 ring/tree 可能多一点点转发冗余，但数量级仍由「每人要补齐 6 个数」决定。

因此更准确的说法是：

有用带宽（字节）延迟敏感（调用次数）
A1 8× broadcast≈ 24S最差（8 次启动）
A2 4× broadcast≈ 24S中等（4 次）
B 1× all-gather≈ 24S最好（1 次）

作业用多次 broadcast 是为了实现简单、和「每个 Parameter 有一个 owner」对齐；生产 ZeRO 更爱打包 + all-gather，主要吃的是 少 α，不是「少搬了 3/4 的权重字节」。

8.5 若问「每卡发出/收到多少」——ring all-gather 直觉

以常见 ring all-gather 为例（N=4，每卡分片大小 Mshard=2S）：

  • 算法上大约走 N−1 = 3 步；每步每卡发出一块分片、收入一块分片。
  • 故每卡发送 ≈ 3·2S = 6S，每卡接收 ≈ 6S（正好补齐缺的 6 个元素）。

对 A2（每个 owner 做一次大小 2S 的 broadcast）：理想树上每卡作为非 owner 时会收到 3 个别人的分片 → 接收仍是 6S。和 all-gather 的「每卡接收有用字节」对齐。

底层 NCCL 具体拓扑（ring / tree）可能让「线上总跳数」略多于有用下界，但比较 A vs B 时， 先比有用字节（这里都是 24S），再比调用次数（α），就不会再把「1 次集体」误当成「1 份流量」。

8.6 收束

  1. 流量按字节算，不按「调用了几次算子」算。
  2. 对齐新 W：A 与 B 的有用流量都是「每卡补齐别人的分片」→ 玩具里都是 24S。
  3. all-gather「次数更少」赢在 α（延迟）；不是自动赢在「总带宽少 3/4」。
  4. 8× 比 4× 更碎：字节仍约 24S，但 α 更大，小消息更不划算。
